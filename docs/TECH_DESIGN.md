# 자소서 서비스 MVP 기술 설계서

> 이 문서는 완료된 Next.js v1과 해당 `/api/drafts`의 계약을 보존한다. 현재 개발 기준은 Python·Vue·FastAPI·LangGraph·MCP를 활용하는 [v2 기술 설계](TECH_DESIGN_V2.md)다. 2026-10-20 ESSAY-19 공통 기반·ESSAY-10 조사·ESSAY-21 계획/평가/분기 계약을 완료했다. 실제 네 역할 연결과 새 업무 API는 ESSAY-14에서 구현한다. 아래 최대 2회 호출 및 오케스트레이션 제외 규칙은 v1에만 적용한다.

- 기준일: 2026-10-19
- 제품 요구사항: [PRD.md](PRD.md), R1~R5
- 공통 계약: [ESSAY-1](https://kmskojb.atlassian.net/browse/ESSAY-1)
- 목적: 프런트엔드·백엔드·QA가 같은 규격으로 병렬 개발하고 결과를 검증한다.

## 1. 구성과 기술 선택

새 저장소는 Next.js + TypeScript 단일 프로젝트를 기본으로 한다. 기존 구현이 있다면 기존 기술과 구조를 먼저 확인하고, 같은 제품 요구사항과 API 계약을 구현한다. 별도 백엔드 서버나 데이터베이스는 이번 MVP에 필요하지 않다.

```text
브라우저의 입력·결과 화면
        │ POST /api/drafts
        ▼
서버 입력 검증 → 실제 LLM 호출 → 응답 형식 및 글자 수 검증
                                      │ 범위 밖이면 한 번 재작성
                                      ▼
                           최종 성공·보완 안내·오류 응답
        │
        ▼
원본 경험 비교 → 결과 편집 → 글자 수 갱신 → 복사
```

한 HTTP 요청에서 최종 결과를 반환하는 방식으로 구현한다. SSE·MCP·서비스 내부 에이전트 오케스트레이션은 추가하지 않는다. OMO의 개발 에이전트와 제품의 모델 호출은 별개다.

v1은 OpenAI Responses API와 `gpt-5.6-terra`, 추론 설정 `low`로 검증했다. 실제 환경변수 이름과 실행 방법은 README, 사실 보존 방식은 `docs/decisions/factual-drafting.md`를 따른다. v2의 모델·검색 어댑터 호환성은 별도 확인한다.

## 2. 파일 구조와 담당 범위

아래 경로는 새 Next.js 프로젝트의 기준이다. 기존 저장소에서는 같은 책임을 가진 경로에 대응시킨다.

| 범위 | 역할 | 연결 티켓 |
| --- | --- | --- |
| 프로젝트 설정, `src/shared/`, `README.md`, 공통 문서 | 메인이 조율하고 실제 수정 담당자를 한 명 지정 | ESSAY-1 |
| `src/app/page.tsx`, `src/app/globals.css`, `src/components/essay/` | 프런트엔드 | ESSAY-2, ESSAY-3 |
| `src/app/api/drafts/`, `src/server/`, 내부 단위 테스트 | 백엔드 | ESSAY-4, ESSAY-5 |
| `tests/`, 테스트 샘플, `docs/qa.md` | QA | ESSAY-6, ESSAY-7 |

`src/shared/`에는 API 요청·응답 타입, 길이 상수, 줄바꿈 정규화·글자 수 계산 함수를 둔다. 서버 자격증명과 모델 호출 코드를 공통 모듈에 넣지 않는다. 프런트엔드는 공통 타입과 함수만 가져온다.

설정·공통 코드·API 계약 변경은 메인이 조율한다. 같은 파일을 여러 작업자가 동시에 수정하지 않도록 소유권과 작업 순서를 정한다. QA는 제품 코드 결함을 구현 담당자에게 전달하고, 다른 작업자의 변경을 되돌리지 않는다.

## 3. API 계약

### 요청

`POST /api/drafts`, `Content-Type: application/json`

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `company` | string | 기업명 |
| `role` | string | 지원 직무 |
| `question` | string | 자기소개서 문항 |
| `experience` | string | 사용자가 제공한 실제 경험 |

모든 필드는 필수 문자열이다. 누락, 잘못된 타입, 빈 문자열, 공백만 있는 문자열은 모델 호출 전에 거부한다. JSON 요청을 해석할 수 없는 경우도 입력 오류로 처리한다. 화면 검증과 별도로 서버 검증을 수행한다.

### 응답

| HTTP | 응답 형태 | 의미 |
| --- | --- | --- |
| 200 | `{ status: "ready", draft: string, characterCount: number, generationCalls: number }` | 길이 조건을 통과한 초안 |
| 200 | `{ status: "needs_input", message: string, generationCalls: number }` | 추가 경험이나 설명이 필요함 |
| 400 | `{ status: "error", code: "INVALID_INPUT", message: string, fieldErrors: object }` | 잘못된 입력 |
| 422 | `{ status: "error", code: "LENGTH_RETRY_EXHAUSTED", message: string }` | 한 번 재작성한 뒤에도 길이 조건 불충족 |
| 502 | `{ status: "error", code: "MODEL_ERROR", message: string }` | 모델 호출 실패 또는 응답 형식 오류 |
| 504 | `{ status: "error", code: "MODEL_TIMEOUT", message: string }` | 모델 호출 제한 시간 초과 |
| 500 | `{ status: "error", code: "CONFIG_ERROR", message: string }` | 필요한 모델 설정 누락 또는 오류 |

`fieldErrors`의 필드별 메시지는 요청 필드 이름을 키로 사용한다. 요청 본문 자체를 해석할 수 없으면 전체 오류는 `message`로 안내하고 `fieldErrors`는 빈 객체로 반환할 수 있다.

`characterCount`는 반환하는 최종 초안에서 서버가 계산한다. `generationCalls`는 해당 요청에서 실제로 시도한 모델 호출 횟수이며 성공 및 보완 응답에서는 1 또는 2다. 모델이 생성한 숫자를 그대로 사용하지 않는다.

실패 응답에는 실패한 초안, 내부 오류 상세, API 키를 포함하지 않는다. 오류 계약에 없는 호출 횟수는 테스트의 모델 호출 기록에서 검증한다. `needs_input`은 정상적인 보완 요청이며 일반 오류와 구분한다.

## 4. 글자 수 규칙

- 목표 길이: 1,000자. 성공 범위: **801~1,000자, 양 끝 포함**.
- `\r\n`과 `\r`을 `\n`으로 정규화한다.
- 공백과 줄바꿈을 포함해 Unicode 코드 포인트 수를 센다.
- 계산 과정에서 공백을 제거하거나 임의로 잘라 길이를 맞추지 않는다.
- 화면과 서버가 같은 공통 함수를 사용한다. JavaScript 문자열의 `.length`만으로 계산하지 않는다.
- 반환·편집하는 초안과 계산 대상은 같은 줄바꿈 정규화 규칙을 적용한다.

기준 계산식은 `Array.from(text.replace(/\r\n?/g, "\n")).length`다. 이는 화면에서 보이는 글자 묶음 수와 다를 수 있다. 예를 들어 `가`와 단일 이모지 `😀`는 각각 1이며, 여러 코드 포인트가 결합된 이모지는 1로 세지 않는다. 별도의 Unicode 조합 정규화는 적용하지 않는다.

| 초안 길이 | 최초 생성 이후 | 한 번 재작성한 이후 |
| --- | --- | --- |
| 800 이하 | 한 번 재작성 | 422 오류 |
| 801~1,000 | 성공 | 성공 |
| 1,001 이상 | 한 번 재작성 | 422 오류 |

정보 보완 메시지에는 초안 길이 규칙을 적용하지 않는다. 사용자 편집 결과는 범위를 벗어나도 경고와 복사를 제공하며, 자동으로 모델을 다시 호출하지 않는다.

## 5. 모델 호출과 재작성 흐름

1. 요청 입력과 서버 모델 설정을 확인한다.
2. 기업·직무·문항·경험을 전달해 모델을 한 번 호출한다. 초안 또는 보완 필요 응답을 구분할 수 있는 구조화된 형식을 요구한다.
3. 서버에서 응답 구조를 검증한다. 기대한 종류·필드·문자열이 없으면 `MODEL_ERROR`로 종료한다.
4. 보완 필요 응답이면 `needs_input`으로 종료한다. 분량을 늘리기 위한 재작성은 하지 않는다.
5. 초안이면 줄바꿈 정규화 후 실제 글자 수를 계산한다. 유효 범위면 `ready`로 반환한다.
6. 범위 밖이면 최초 입력, 원본 경험, 기존 초안, 실제 글자 수, 801~1,000자 목표 범위를 전달해 한 번만 재작성한다.
7. 두 번째 응답도 같은 형식·길이 검증을 수행한다. 유효한 초안은 성공, 보완 필요는 보완 안내, 다시 범위 밖인 초안은 `LENGTH_RETRY_EXHAUSTED`로 종료한다. 세 번째 호출은 없다.

모델의 작성 지시는 처음 생성할 때와 재작성할 때 모두 다음을 유지한다.

- 제공된 경험을 문항·직무에 맞게 정리한다.
- 없는 경력·수상·성과 수치를 추가하지 않는다.
- 정보가 부족하면 어떤 내용을 보완할지 안내한다.
- 사실 추가, 무의미한 반복, 공백 채우기로 분량을 맞추지 않는다.
- 경험 입력에 없는 성과를 만들어 달라는 요구가 있어도 사실 추가 금지 원칙을 유지한다.

길이 검증은 사실성을 보증하지 않는다. 경험 반영과 허위 사실 여부는 샘플 평가 및 프로젝트 작성자의 최종 확인으로 검증한다.

### 호출 제한과 설정

- 요청당 실제 모델 호출은 최대 2회다. 길이 조건에 따른 두 번째 호출만 허용한다.
- 모델 호출 한 번의 제한 시간은 30초다. 시간 초과 시 해당 호출을 취소하고 종료한다.
- SDK의 자동 재시도를 비활성화한다. 서버·모델 래퍼·화면의 숨은 자동 재시도도 없어야 한다.
- 모델 호출 실패, 시간 초과, 응답 형식 오류는 길이 재작성 조건이 아니다. 해당 오류로 즉시 종료한다.
- 모델명과 API 키는 서버 환경변수로 관리한다. `.env.example`에는 필요한 변수 이름과 빈 값만 두고, 실제 키는 브라우저 코드와 저장소에 포함하지 않는다.
- 키가 없으면 모의 모델로 독립적인 구현·테스트를 진행할 수 있지만, 실제 모델 연결과 샘플 검증은 미검증으로 기록한다.

## 6. 화면 상태와 데이터

| 상태 | 화면 동작 |
| --- | --- |
| 입력 대기 | 네 입력을 편집하고 필수 항목을 확인한다. |
| 생성 중 | 입력과 생성 버튼을 잠근다. 한 번의 HTTP 요청이 끝날 때까지 생성 중으로 표시한다. 서버의 재작성도 이 상태에 포함된다. |
| 성공 | 요청 당시 경험과 초안을 함께 표시한다. 편집, 글자 수, 범위 경고, 복사를 제공한다. |
| 정보 보완 필요 | 보완 안내와 기존 입력을 표시하고 수정 후 다시 요청할 수 있게 한다. |
| 오류 | 사용자용 오류 안내와 기존 입력을 유지하고 다시 요청할 수 있게 한다. |

요청 전 경험을 스냅샷으로 보관해 결과와 짝지어 표시한다. 사용자가 다음 요청의 입력을 수정해도 이전 초안이 다른 경험에서 생성된 것처럼 표시하지 않는다.

결과 편집 시 공통 함수로 글자 수를 갱신한다. 800자 이하는 부족, 1,000자 초과는 초과로 안내한다. 복사 대상은 현재 편집 문자열이며 복사 실패도 안내한다. 상태와 내용은 브라우저 메모리에서 관리하고, 서버 저장이나 새로고침 복구는 구현하지 않는다.

## 8. 검증 계획

### 모의 모델을 사용하는 결정적 검증

| 사례 | 기대 결과 |
| --- | --- |
| 누락·빈 값·공백만 있는 입력·잘못된 타입 | 400, 모델 호출 0회 |
| 최초 초안 801자 또는 1,000자 | 200 ready, 호출 1회 |
| 최초 800자 → 유효 길이 | 200 ready, 호출 2회 |
| 최초 1,001자 → 유효 길이 | 200 ready, 호출 2회 |
| 두 번째 초안도 범위 밖 | 422, 호출 2회, 세 번째 호출 없음 |
| 최초 보완 필요 응답 | 200 needs_input, 호출 1회, 길이 재작성 없음 |
| 재작성에서 보완 필요 응답 | 200 needs_input, 호출 2회, 추가 호출 없음 |
| 모델 호출 실패·응답 형식 오류·시간 초과 | 해당 오류 반환, 그 뒤 추가 호출 없음 |
| 모델 설정 누락 | 500 CONFIG_ERROR, 모델 호출 없음 |
| 공백·LF·CRLF·CR·한글·단일 및 결합 이모지 | 공통 계산 규칙과 일치하며 화면·서버 결과 동일 |

실제 API 경로에서 요청·응답 계약과 호출 횟수를 검증한다. 모델 응답은 제어 가능한 대체 모듈로 주입하고, 테스트용 초안이 800·801·1,000·1,001자임을 공통 규칙으로 확인한다. QA는 기대 결과와 실제 결과가 다른 경우 입력·재현 순서·증거를 기록해 담당자에게 전달한다.

### 실제 화면 및 실제 모델 검증

- 입력 → 생성 → 원본 비교 → 편집 → 복사 후 붙여넣기를 실제 브라우저에서 수행한다.
- 생성 중 중복 요청 방지, 오류 시 입력 유지, 보완 후 재요청, 범위 밖 편집 내용의 경고·복사를 확인한다.
- 실제 모델로 일반 경험 2개, 정보 부족, 긴 경험, 없는 성과 추가 요구의 고정 샘플 5개를 실행한다.
- 샘플별 최종 글자 수, 호출 횟수, 경험 반영, 문항 적합성, 허위 사실 여부를 `docs/qa.md`에 기록한다. 초안이 없는 보완·오류 응답의 글자 수는 해당 없음으로 기록한다.
- 프로젝트 작성자의 사실성 확인 전에는 ESSAY-7을 검토 대기로 유지한다.

설정된 빌드·정적 검사와 관련 테스트를 실행한다. 실제 실행하지 않은 검사, 실제 모델 자격증명 부재로 수행하지 못한 검증, 미해결 결함은 통과로 처리하지 않는다.

## 9. 인계 산출물

구현 완료 시 README에 실행 방법, 필요한 환경변수 이름, 실제 선택한 모델, 테스트 실행 방법, 3분 시연 순서를 기록한다. `docs/qa.md`에는 모의 응답 테스트와 실제 모델·브라우저 검증을 구분하고, 남은 한계와 사용자 확인 항목을 남긴다.

기획 요구사항이 바뀌면 [PRD.md](PRD.md), 구현 계약이 바뀌면 이 문서, 작업의 범위·완료 조건이 바뀌면 해당 Jira 티켓을 함께 갱신한다. 중요한 기술 결정을 바꿀 때에는 선택 이유와 대안을 ADR로 남기되, 사소한 구현 선택마다 별도 문서를 만들지는 않는다.
