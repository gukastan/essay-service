# 자소서 서비스 MVP 기획서 및 PRD

> 이 문서는 완료된 v1(ESSAY-1~7)의 범위와 계약이다. 2026-10-19에 승인된 다음 개발 방향은 [v2 PRD](PRD_V2.md)이며, [v2 백로그](BACKLOG_V2.md)에서 추적한다. 아래의 제외 범위·호출 횟수·3일 일정은 v1에 적용된다. v2는 아직 미구현이다.

- 기준일: 2026-10-19

- 공통 기준 및 작업 시작점: [ESSAY-1](https://kmskojb.atlassian.net/browse/ESSAY-1)

## 1. 목적과 사용자

자기소개서 작성이 막막한 취업 준비생이 자신의 경험을 지원 기업·직무·문항에 맞는 초안으로 정리하도록 돕는다. 사용자는 AI가 작성한 내용을 자신의 경험과 비교하고, 수정한 뒤 복사해 활용한다.

사용자 경험을 바탕으로 작성 시간을 줄이는 것이 목적이다. 사용자가 제공하지 않은 사실을 만들어 분량을 채우거나 합격 가능성을 예측하지 않는다.

## 2. 사용자 흐름

1. 기업명, 지원 직무, 자기소개서 문항, 본인의 경험을 입력한다.
2. 생성 버튼을 누르면 실제 언어 모델이 초안을 작성한다.
3. 서버가 글자 수를 검사하고, 범위를 벗어난 경우 한 번 재작성한다.
4. 사용자는 요청 당시 입력한 경험과 최종 초안을 함께 확인한다.
5. 초안을 편집하면서 글자 수를 확인하고 현재 내용을 복사한다.

정보가 부족하면 보완할 내용을 안내한다. 생성에 실패하면 오류를 안내하고 기존 입력을 유지해 다시 요청할 수 있게 한다.

## 3. 필수 요구사항

| ID | 요구사항 | 완료 기준 | 연결 티켓 |
| --- | --- | --- | --- |
| R1 | 기업명·직무·문항·경험 입력 | 네 항목 모두 필수다. 빈 값과 공백만 있는 값은 안내하며, 서버에서도 모델 호출 전에 거부한다. | ESSAY-2, ESSAY-4, ESSAY-6 |
| R2 | 경험에 근거한 초안 작성 | 없는 경력·수상·성과 수치를 추가하지 않는다. 작성에 필요한 정보가 부족하면 추가 입력을 요청한다. | ESSAY-4, ESSAY-7 |
| R3 | 글자 수 검증과 한 번의 재작성 | 목표는 1,000자이며 유효한 초안은 801~1,000자다. 800자 이하 또는 1,000자 초과이면 한 번 재작성한다. 재작성 후에도 범위를 벗어나면 실패로 안내한다. | ESSAY-3, ESSAY-5, ESSAY-6 |
| R4 | 원본 비교·편집·복사 | 요청 당시 경험과 초안을 함께 표시한다. 편집할 때 글자 수를 갱신한다. 범위를 벗어난 편집 내용은 경고하되 복사를 허용한다. 복사 대상은 현재 편집 내용이다. | ESSAY-3, ESSAY-7 |
| R5 | 진행 및 실패 상태 처리 | 생성·재작성 중 입력과 생성 버튼을 잠가 중복 요청을 막는다. 오류와 정보 보완 응답에서 입력을 유지하고 다시 요청할 수 있다. | ESSAY-2, ESSAY-4, ESSAY-5, ESSAY-6, ESSAY-7 |

글자 수는 공백·줄바꿈을 포함한다. 줄바꿈을 LF로 통일한 뒤 Unicode 코드 포인트 단위로 계산하며, 화면과 서버가 같은 계산 규칙을 사용한다. 모델이 출력한 글자 수를 신뢰하지 않고 코드로 계산한다.

정보 보완 안내는 자기소개서 초안이 아니므로 801~1,000자 조건과 길이 재작성 대상에 포함하지 않는다. 사용자의 수동 편집도 자동 재작성을 유발하지 않는다.

## 4. 이번 프로젝트의 범위

포함: 단일 입력·결과 화면, 실제 모델 연결, 글자 수 검사, 한 번의 재작성, 정보 보완·오류 안내, 편집·복사, 테스트와 시연 안내.

제외: 로그인, 서버 저장, 새로고침 이후 내용 복구, 채용 공고 수집, 결제, 합격 예측, 서비스 내부의 멀티에이전트, 서비스 자체의 Jira 자동 연동.

OMO의 개발 역할 분담과 Jira 작업 관리는 개발 과정에서 사용한다. 사용자에게 제공하는 자소서 서비스 기능에는 포함하지 않는다. 공개 배포 URL은 필수 제출 조건이 아니다.

## 6. 최종 완료 기준

- [ ] README 안내대로 환경을 설정하고 서비스를 실행할 수 있다.
- [ ] 실제 모델을 사용해 입력 → 생성 → 결과 확인 → 편집 → 복사가 동작한다.
- [ ] R1~R5 및 각 Jira 티켓의 완료 조건을 검증했다.
- [ ] 800·801·1,000·1,001자 경계와 재작성 횟수 제한을 확인했다.
- [ ] 실제 모델 샘플 5개를 평가했다: 일반 경험 2개, 정보 부족, 긴 경험, 없는 성과 추가 요구.
- [ ] 샘플별 최종 글자 수, 호출 횟수, 경험 반영, 문항 적합성, 허위 사실 여부를 기록했다.
- [ ] 프로젝트 작성자가 최종 사실성 평가를 확인했다. 확인 전에는 ESSAY-7을 검토 대기로 남긴다.
- [ ] 모의 응답 테스트와 실제 모델 검증을 구분해 기록하고, 미해결 문제와 미검증 항목을 공개했다.
- [ ] 실행 방법과 3분 시연 순서가 준비되었다.

## 7. OMO가 문서를 활용하는 방법

PRD → 기술 설계서 → ESSAY-1~7의 순서로 읽고 작업을 배정한다. PRD는 기능 범위와 사용자 관점의 완료 기준, 기술 설계서는 구현 계약, Jira는 작업별 담당·의존관계·진행 기록의 기준으로 사용한다.

최신 사용자 지시와 승인된 변경 기록을 함께 확인한다. 문서와 티켓의 기능 범위·완료 기준이 충돌하면 임의로 한쪽을 덮어쓰지 않고 차이를 확인한다. 구현 선택이나 요구사항이 바뀌면 관련 문서와 티켓을 함께 갱신해 일치시킨다. 중요한 기술 선택을 변경할 때만 이유와 대안을 짧은 ADR로 남긴다.
