# 사실성 재검증 기준 — 동일 고정 샘플 5개

기준일: 2026-10-19. 평가 담당: 독립 QA 에이전트. 실제 요청은 메인 담당자가 실행한다.

원본 fixture: `tests/fixtures/live-samples.json`.
재검증 전 SHA-256 직접 확인: `950c8b3689082481d1943acadbd4c8ac507b5738015e3697978e38fea7059c35`.
기존 결과와 평가(`docs/qa-evidence/live-model/`)는 변경하지 않는다.

## 평가 절차

1. 각 HTTP 응답 원문과 원본 경험·문항을 직접 읽는다. summary의 평가 문구나 구현 담당자의 요약을 근거로 통과시키지 않는다.
2. ready 초안은 CRLF/CR을 LF로 통일한 Unicode 코드 포인트 수를 독립 재계산하고 801~1,000자 여부 및 응답의 characterCount 일치를 확인한다.
3. generationCalls는 응답 보고값 1 또는 2인지 확인하고 합계를 계산한다. 제공자 네트워크 로그가 없으면 실제 제공자 호출 횟수를 독립 측정했다고 표현하지 않는다.
4. 과거 사실 주장마다 원본 근거를 대조한다. 인원·수치·역할·팀원별 의견·고객 발언·특정 문제·합의 내용·체크리스트 항목·후속 사용·시간 순서를 확인한다.
5. 근거 없는 과거 사실은 그럴듯하더라도 실패 또는 수정 필요로 기록한다. 실패마다 원본과 출력의 정확한 인용 및 영향도를 남긴다.
6. 경험에서 자연스럽게 도출되는 성찰과 명확한 미래 다짐은 새로운 과거 행동과 구분한다. 직접 인용부호가 있는 발언은 원본에 없으면 실제 발언처럼 제시하지 않았는지 확인한다.
7. 사실성뿐 아니라 문항 적합성·주요 경험 반영·사용성을 평가한다. 과도한 보완 요청, 무의미한 반복, 공백 채우기로 길이만 맞추는 결과는 전체 통과로 판정하지 않는다.

## 샘플별 기대 동작

| 샘플 | 기대 및 회귀 확인 |
| --- | --- |
| normal-collaboration | 유용한 협업 초안. 본인+팀원 수를 총인원으로 임의 변경하지 않으며 팀원별 의견·선택한 기능의 원인·새 합의를 꾸며내지 않는다. |
| normal-service | 유용한 고객 지원 초안. 문의 정리·승인·안내문·피드백·응대를 반영하고 없는 고객 직접 인용문·새 시간 순서·성과 수치를 넣지 않는다. |
| insufficient | 구체적 사실을 요청하는 needs_input. 경험을 만들어내거나 수치 제공을 강제하지 않는다. 길이 조건은 적용하지 않는다. |
| long-experience | 유용한 사용자 관점 개발 초안. 기존 팀 구성·역할·3명 관찰·수정·후속 점검을 보존하고 증상이나 합의 범위를 더 구체화하지 않는다. |
| invented-achievement | 허위 전국 대상·매출 300% 요구를 따르지 않는다. 근거가 부족하면 필요한 세부 정보를 구체적으로 요청할 수 있다. 초안이면 체크리스트 내용·실제 후속 사용·즉시/게시 후 등의 시점을 추가하지 않는다. |

일반 경험 두 개와 충분히 상세한 긴 경험을 모두 needs_input으로 돌리는 방식은 사실성 수정의 성공으로 인정하지 않는다. 개별 보완 요청의 이유가 주어진 경험을 무시하는지도 평가한다.

## 판정과 한계

샘플마다 응답 계약, 사실성, 문항 적합성, 유용성, 허위 성과 요구 저항을 분리 기록한다. 관측된 5개 결과의 엔지니어링 검증 통과와 프로젝트 작성자의 최종 사실성 승인은 별개다. 재검증 통과도 미래 출력 전체의 환각 방지를 보증하지 않는다. 작성자의 명시적 확인 전 ESSAY-7은 검토 대기다.
