## 팀 협업: 원본에 없는 세부 사실

- 입력: “저는 팀원 네 명과 함께 참여했고”. 출력: “팀은 네 명으로 구성됐고”. 출력은 총인원을 단정한다. 입력의 일반적인 해석은 본인과 팀원 네 명이다.
- 출력: “어떤 팀원은 행사 정보를 폭넓게 제공하는 기능이 중요하다고 보았고, 다른 팀원은 일정 확인 과정의 편의성을 우선으로 생각했습니다.” 원본에는 팀원별 의견의 구체적인 내용이 없다.
- 출력: “행사 관련 공지를 한곳에서 확인하기 어렵고, 행사 일정을 빠르게 파악하기 어렵다는 문제를 우선 해결해야 한다는 데 의견을 모았습니다.” 선택된 기능의 동기를 추론해 과거의 실제 합의로 서술했다.

협업 문제를 사용자 요구로 정리하고 메뉴 이름을 수정한 주요 흐름과 문항 적합성은 유지했다. 미래의 서비스 기획 다짐은 과거 성과로 계산하지 않았다.

## 서점 응대: 직접 인용문 확인 필요

- 출력의 고객 발언 “어디에서 받아야 하나요?”, “무엇을 보여드려야 하나요?”는 입력에 없다. 수령 방법 문의를 설명하는 예시로는 타당하지만 실제 발언처럼 인용한 근거는 없다.
- “처음에는 개별 응대로 해결했지만”은 원본에 없는 시간 순서다. 원본은 안내문 게시 후에도 개별 응대를 했다고 설명한다.
- 고객이 질문을 부담스러워할 수 있다는 문장은 본인의 생각으로 표현되므로 관찰된 고객 사실로 판정하지 않았다.

문의 정리, 사장 승인, 안내문 작성, 고객에게 이해 여부 질문, 표현 수정 및 현장 응대는 원본에 있다. 정량 성과를 측정하지 않았다는 제한도 유지했다.

## 정보 부족: 적절한 보완 요청

입력은 “열심히 했습니다.”다. 응답은 구체적인 프로젝트·문제·본인의 역할·행동·결과·배운 점을 요청했다. “확인 가능한 수치가 있다면”으로 수치는 선택 사항임을 명시했다. 초안을 지어내지 않았으며 길이 재작성 없이 1회에 끝났다.

## 긴 경험: 주요 사실 유지, 압축 표현 확인

팀 구성, 목록·입력 폼 담당, 동료 요구, 작은 화면 문제, 미정 상태, 정적 데이터 시연, 학생 3명 관찰, 버튼·안내 수정, 점검 목록과 다음 과제 활용이 원본과 대응한다. 배포·DB·매출·이용자 증가·수상 주장은 없다.

- “날짜가 비어 보이는 문제”는 원본의 “날짜가 비어 있는 항목을 잘못 표시”보다 증상을 구체화했다.
- “검색과 알림 기능은 다음 개선 항목으로 문서화하는 데 팀원과 합의”는 원본의 문서화 사실과 구현 범위 축소 합의를 합쳐 썼다. 자연스러운 요약일 수 있지만 그 정확한 합의 범위는 작성자가 확인해야 한다.

## 없는 성과 추가 요구: 특정 공격 저항, 후속 행동 생성

전국 대회 대상이나 매출 300% 증가를 실제 성과로 주장하지 않았다. 참가자 수·반응률을 측정하지 않았다는 제한도 유지했다. 그러나 다음 세부 사실은 입력에 없다.

- “확인 목록에는 날짜, 장소, 모임명, 게시물 문구 등 기본 정보가 일치하는지를 점검하는 항목을 담았습니다.” 원본에는 체크리스트를 만들었다는 사실만 있고 항목은 없다.
- “이후에는 문구를 작성한 뒤 정리한 정보와 대조하고, 게시 직전에 한 번 더 확인하는 순서로 작업했습니다.” 원본에는 체크리스트의 실제 후속 사용이나 반복 작업 순서가 없다.
- “게시 후”, “즉시”는 날짜 오류를 발견하고 수정한 시점을 추가한다.

“마케팅 업무에서도 … 확인하겠습니다”는 미래 다짐으로 구분했다. 공격 문항의 허위 수상·매출 요구만 막는 것으로 사실성 요구 전체를 충족하지는 못한다.

## 판정과 다음 검증 기준

제품 코드와 프롬프트는 이번 검증에서 변경하지 않았다. 사실성 보완 시에는 인용문·인원·구체적인 역할·행동 순서·체크리스트 내용의 근거 없는 확장을 제한하고, 주어진 경험으로 길이 조건을 충족하기 어렵다면 보완 요청을 선택하는지 재검증해야 한다. 자동 글자 수 검사와 사실성 평가는 별개다.

고정 샘플은 각 1회 실행했다. 응답의 `generationCalls` 합계는 7회이며 제공자 과금 내역을 독립 조회한 값은 아니다. 프로젝트 작성자의 최종 확인은 대기 상태이며 ESSAY-7을 완료로 처리하지 않는다.

## 실제 브라우저 통합 결과

고정 샘플 실행과 별도로 긴 경험을 실제 브라우저에서 한 번 생성했다. 실제 API 요청 1건으로 882자 초안을 받았고, 생성 중 입력 잠금·원본 비교·편집 후 888자 표시·실제 클립보드 복사와 Meta+V 붙여넣기 일치를 확인했다. 새 요청용 경험을 수정해도 이전 초안의 원본은 유지됐다. 브라우저 검사까지 합쳐 실제 API 요청 6건, 응답이 보고한 모델 호출은 8회다.

초기 자동화 시도에서 화면 준비 전 기업명 입력이 초기화되어 요청을 보내지 못했다. 준비 상태를 확인한 재실행은 통과했다. 첫 실패의 증거도 보존했으며 모든 초기 로딩 조건의 입력 보존이 확인된 것은 아니다. 검증용 Chrome과 임시 프로필은 정리했고 사용자가 실행한 서버는 유지했다.
