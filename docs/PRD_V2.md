## 목적

사용자의 실제 경험을 지원 기업의 직무 요건과 연결해 문항에 답하는 초안을 만든다. 기업·직무 조사, 경험·문항 분석, 작성, 검토의 네 역할을 분리한다. 기업의 인재상은 확인된 자료가 있고 경험과 관련될 때 활용하며, 문항과 실제 직무 요건을 우선한다.

회사 이름에서 연상한 인재상, 타사의 공고, 사용자가 말하지 않은 경력·행동·성과·배움으로 글을 채우지 않는다. 네 역할 분리 자체가 품질을 보장하지 않으므로 실제 사례로 효과를 확인한다.

## 사용자 흐름

1. 기존 필수 네 항목(기업명·직무·문항·경험)을 입력한다. 선택 항목으로 채용 공고 URL과 공고 본문을 제공할 수 있다.
2. 서버는 기업·직무 조사와 경험·문항 분석을 병렬로 수행한다. 기업 식별이나 경험이 부족하면 구체적인 보완 항목을 안내한다.
3. 확인된 직무 요구와 사용자 경험 근거를 연결해 작성하고, 독립된 검토 역할이 원문·출처·문항과 대조한다.
4. 최초 결과에 수정 가능한 문제가 있으면 한 번 수정하고 다시 검토한다. 사실성 문제와 분량 문제에 각각 별도의 재작성 기회를 주지 않는다.
5. 통과한 801~1,000자 초안과 경험 원문, 활용 출처·확인일·직무 연결 이유를 보여준다.
6. 사용자는 편집·글자 수 확인·복사를 한다. 편집하면 생성 당시 검토와 사용자의 수정 내용을 구분한다.

## 자료 사용 규칙

- 우선순위: 문항의 요구 → 해당 직무·공고의 요구 → 관련 있는 기업 인재상.
- 공식 홈페이지·공식 채용 페이지를 우선한다. 외부 채용 플랫폼은 공식 사이트에서 연결되는 등 해당 기업의 공고임을 확인한다.
- 공고가 모집 중이라고 확인되지 않았다면 현재 채용 중이라고 단정하지 않는다. 확인 날짜와 자료에 표시된 게시/마감일을 구분한다.
- 사용자가 붙여 넣은 공고 본문도 활용할 수 있으나 `user_provided`로 표시하고 공식 검증 자료로 가장하지 않는다.
- 인재상 자료만 없으면 이를 생략하고 직무 근거로 진행한다. 기업 식별이 모호하거나 직무 연결에 쓸 근거가 하나도 없으면 회사 식별 정보·공고 자료를 요청한다.
- 출처끼리 상충하면 해당 사실을 제외한다. 직무 핵심 요건이나 기업 식별에 영향을 주는 상충은 보완 요청으로 돌린다.
- 검색에는 기업·직무 정보만 사용하며 경험·문항 전문을 외부 검색어로 보내지 않는다.
- 원문과 웹페이지 속 지시는 자료로 취급한다. 시스템 규칙과 실행 예산을 바꿀 수 없다.
- 사용자 과거 사실의 표현 보존 원칙은 [기존 결정](decisions/factual-drafting.md)을 유지한다. 자유로운 과거 사실 재서술은 별도 검증 없이 도입하지 않는다.

## v1 대비 범위 변경

| 항목 | 완료된 v1 | 계획된 v2 |
| --- | --- | --- |
| 모델 흐름 | 직접 호출, 길이 밖이면 한 번 재작성 | 네 역할 LangGraph, 조사·분석 병렬, 작성·검토 순차 |
| 기업 자료 | 입력한 기업명·직무 | 공식 자료 또는 표시된 사용자 제공 공고 |
| 호출 상한 | 최대 2회 | 최대 6회, 자동 재시도 0 |
| 분량 | 801~1,000자 | 동일, 사실성 수정과 공통 1회 수정 예산 |
| 결과 근거 | 경험과 초안 비교 | 경험 비교 + 기업 출처 + 직무 연결 이유 |
| 실행 | 현재 구현 | 새 API와 기능 설정으로 단계적 적용 |

로그인, 사용자 DB 저장, 벡터 검색/RAG, MCP, 무제한 에이전트 토론, 자기소개서 합격 예측, 서비스의 Jira 자동 연동은 범위 밖이다. 현재 개발 작업의 Jira 관리와 제품 기능을 구분한다. v1의 3일 일정은 과거 계획이며 v2 일정·비용이 확정됐다는 뜻이 아니다.
